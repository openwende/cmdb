# 审计记录说明

## 审计记录了什么

CMDB 对主机的以下操作都会写审计记录：录入主机（create）、修改主机配置（config_change，包括内置字段和自定义字段）、删除主机（delete），以及每一次归属变更（placement_change：导入资源池、分配到业务、转移、回收到资源池）。业务、集群、模块本身的新建、修改、删除也有审计，但 query_host_changes 只查主机的审计，看不到这些。

查询主机经历过什么，用 query_host_changes：每条记录有 record_id（引用依据时用它）、time（北京时间）、operator（操作人）、主机 ID 和"IP（主机名）"、action（记录类型）；归属变更另有 source（类型）、from 和 to，配置变更另有 changes，录入和删除另有 config。

## 审计不记录操作原因

审计表没有"原因"或"备注"这一列，操作人在界面上也没有地方填写原因；导入、回收接口虽然能带备注参数，但不会保存。所以审计只能说明"谁、在什么时候、把什么从什么改成了什么"，不能说明"为什么"。

两个容易误当成原因的字段：config 是录入时或删除前的配置摘要，不是操作原因；remark 是系统自动补充的说明（例如"该记录未保存变更前归属"），不是操作人写的备注。问到"为什么"时，应陈述记录显示的经过，说明审计中没有记录原因，并建议找操作人确认。

## 操作人

operator 是执行这次操作的登录用户名。没有登录用户的系统操作记为 system。操作人是"谁点的按钮或调的接口"，不一定是这台主机的负责人（负责人看自定义字段"责任团队"）。只读用户（viewer）不能修改任何数据，所以变更记录的操作人只会是编辑者、管理员或 system（见《角色与权限》）。

## 归属变更的 from 和 to

归属变更记录的 from 是变更前主机的全部归属，to 是变更后的全部归属，而不只是"从哪个模块到哪个模块"。写法：

- 在业务里："业务 / 模块"，多个模块用顿号连接，例如"业务 / 模块A、模块B"；
- 在资源池里："资源池 / 目录名"；
- 没有任何归属（例如刚录入、还没导入资源池）："无归属"。

读 from 和 to 时要按集合对比：两边都有的模块是保留的，只在 to 里的是新加入的，只在 from 里的是移出的。例如 from "业务 / 模块A"、to "业务 / 模块A、模块B" 是新增了模块B，主机没有离开模块A，不能说成"从模块A转出"。from 和 to 里的名称是变更当时的名称。

## 归属变更类型

归属变更的 source 只会出现四种：导入资源池、分配到业务、转移、回收到资源池。进出故障机、待回收也是"转移"，要看 to 里的模块名来判断（见《主机流转规则》）。审计页面上有些地方用了别的叫法："归还到资源池"就是"回收到资源池"，"转移模块"就是"转移"。

## 配置变更的 changes

配置变更记录的 changes 是逐字段的变更列表，每项有 field（字段名）、from（变更前的值）、to（变更后的值）。一条记录可以包含多个字段，例如同时改了状态和故障原因。内置字段用原字段名，例如 status、memory（单位 MB）、disk_size（单位 GB）、os_version；自定义字段写作 custom_fields.<字段名>，例如 custom_fields.备份 从 true 变为 false 表示关闭了备份。from 为空表示这次新增了这个字段。

配置没有实际变化的修改不会产生记录。批量修改多台主机时，每台主机各有一条记录，时间通常只差几秒。

## 审计记录的可靠性

归属变更的审计和变更本身在同一个数据库事务里写入，只要归属变了就一定有记录。配置变更的审计是在修改成功之后单独写的，写审计失败不会撤销修改，所以极少数情况下可能出现"配置变了但没有审计记录"。

## 旧审计记录的特殊情况

较早的审计记录格式不完整：

- 有的归属变更记录没有保存变更前的归属，from 为空，remark 写着"该记录未保存变更前归属（早于归属快照上线的旧审计）"。这时只知道变更后在哪，不知道从哪来，要结合这台主机更早的记录推断。
- 有的记录只保存了模块 ID 没有模块名，显示为"模块名（按当前名称）"，表示用的是模块现在的名称，当时可能叫别的；找不到名称时显示为"模块 #ID"。

## 跨业务主机的位置写法

一台主机同时在两个业务的模块里时（后端允许，但很少见），from 和 to 只会显示其中一个业务的名称，模块名则全部列出。这时"业务 / 模块A、模块B"里的模块不一定都属于前面写的那个业务，需要用 get_host 查看每个归属所在的业务。

## 按模块查询审计

query_host_changes 可以按 module_id 过滤：归属变更按"变更前或变更后在这个模块"匹配；配置变更、录入、删除按"变更发生时主机在这个模块"匹配，也就是这台主机在这条记录之前最近一次归属变更后的位置。在此之前从来没有过归属变更的主机，不属于任何模块，按模块查不到它的配置变更。

## 时间和时区

query_host_changes 输出的时间都是北京时间，since 和 until 也按北京时间理解；until 只写日期时包含当天全天。审计页面上的时间也显示为北京时间，但审计页面的日期筛选仍按 UTC 整天计算：筛选某一天，实际范围是北京时间当天 08:00 到次日 08:00，所以北京时间凌晨 0 点到 8 点之间的操作会被算到前一天。用审计页面核对 AI 的结论时，要注意这个差异。
