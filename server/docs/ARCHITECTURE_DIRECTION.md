## 1. 为什么需要这份文档(现状诊断)

本仓库的拓扑/资源真相层目前处于**"自然语言生成后的失控状态"**:同一份"业务拓扑/资源"被 **3–5 套实现并存**地表达,互不为准:

- **legacy 旧表**(`sets` / `modules` / `host_module_relations`):当前**生产唯一写真相**。
- **mainline**(`mainline_instances`):[`MAINLINE_MODEL_PROPOSAL.md`](./MAINLINE_MODEL_PROPOSAL.md) 的正统实现,但**没走完**(只到"兼容写")就被下面的 v2 截胡,读路径已被架空。
- **v2 图**(`resources_v2` / `edges_v2` + `core/resource_graph` + `core/projection`):HTTP 层"优先命中"的投影,但**无任何设计文档背书**、一次性 AI 生成、8 条数据一致性硬伤未修、**且是 dev-only**(不在 canonical 迁移,仅 `ENABLE_COMPAT_AUTOMIGRATE=true` 运行时建表)——**纯生产部署下 v2 表根本不存在、拓扑静默回退 legacy,"v2 已上位"是 dev 假象**。
- **A 套**(`models` / `model_instances`)与 **B 套**(`dynamic_models` / `resources`):两套并行的"动态模型/自定义 CI"实现,B 的元数据从 A 复制。

对一个**内部平台**,"多套并存、够用就行"还能忍;对一个要**开源、对标蓝鲸**的产品,这是劝退级硬伤——没人会在生产里信任、也没人会给"不知道该信哪套表"的核心提 PR。**收敛真相层,是这个产品能不能成立的前提。**

## 2. 产品定位

| 维度 | 定位 | 推论 |
|---|---|---|
| 性质 | **开源产品,下一代蓝鲸**,对标并**超越** bk-cmdb(非内部平台) | 代码纯净度 / 架构的可讲述性**本身就是产品的一部分**,与功能同等重要 |
| 规模 | **10 万**资源量级,**不过早优化**(真到百万再说) | 砍掉过早优化:分区表、懒投影/批量回填、GIN/JSONB 调优全不需要;用**最朴素、最可信、最好读**的 PostgreSQL 建模 |

**"下一代"的差异点**:蓝鲸有的(动态模型 / 主线拓扑 / 实例关系)我们要有;蓝鲸没有的——**AI 原生能力 + agent 工具化(MCP)**——是我们超越它的地方。

## 3. 终局架构:三层骨架 + AI 基座

源自 [`MAINLINE_MODEL_PROPOSAL.md`](./MAINLINE_MODEL_PROPOSAL.md) 的三层架构,向上补一层 AI 基座:

```
┌───────────────────────────────────────────────────────────┐
│  AI 基座            NL 查询 · 自动发现 · 变更影响分析 · drift 检测   │
│                  —————  经 MCP 暴露给外部 agent  —————          │
├───────────────────────────────────────────────────────────┤
│  第三层  业务拓扑产品语义        /api/v1/topology(稳定外壳)        │
├───────────────────────────────────────────────────────────┤
│  第二层  mainline 主线          业务拓扑这棵树(有约束、高频、树形)    │
├───────────────────────────────────────────────────────────┤
│  第一层  通用动态模型 + 可信关系图   任意资源 / 任意关系 / 依赖与影响分析  │
├───────────────────────────────────────────────────────────┤
│  横向能力     强身份 + 幂等  ·  事件流  ·  期望态 vs 实际态对账        │
└───────────────────────────────────────────────────────────┘
```

- **第一层 通用动态模型 + 可信关系图**:模型元数据 + 实例 + **任意类型间的关系图**。承载主机/网络设备/中间件/数据库/任意自定义 CI,以及"变更影响分析"所需的跨类型依赖遍历。
- **第二层 mainline 主线**:业务拓扑(`business→set→module`)是一棵**有约束的树**(固定层级、唯一父、默认节点、排序、路径)。它**不是**任意图——用树模型而非通用图来保证约束与高频查询效率(见原则 §4.3)。
- **第三层 业务拓扑产品语义**:对外保持 `/api/v1/topology/*` 的稳定外壳,底层由 mainline 驱动,前端无需理解元模型。
- **AI 基座**:把第一/二层的查询与分析能力,通过 **MCP/工具接口**暴露给 agent 编排,而不是在 CMDB 里内置 chatbot。
- **横向能力**:强身份/幂等(自动发现的命根)、事件流(NL 的"上周变更"、审计)、期望态 vs 实际态(异常检测的本质)。

## 4. 核心设计原则

1. **单一可信源。** 一个实体一份真相。多套并存是当前最大的债,收敛它优先于一切新功能。
2. **强身份 + 幂等。** 每类资源有明确身份键;同一资源重复写入(尤其自动发现)必须幂等、不产生重复/孤儿。
3. **别为 AI 过度图化。** 四类 AI 能力里**只有"影响分析"真需要图**;NL 查询要强 schema、自动发现要幂等 upsert、异常检测要事件流+对账。图是服务于"关系/影响"的专用工具,**不是万能基座**——树归树、图归图、实例归实例,各用最合适的结构。
4. **CMDB 是 agent 的工具,不是内置聊天框。** 本分是成为 AI 可信赖的事实源与工具(MCP),把自然语言理解和编排交给外部 agent。
5. **期望态 vs 实际态分离。** CMDB 存 desired state,采集器报 actual state,对账产生 drift——这是 CMDB 从"记录系统"升级为"控制系统"的分水岭。
6. **为 10 万设计,不为百万。** 简单可信 > 性能花哨。Postgres 单库 + 普通索引足矣。性能优化等真有规模压力时再做。
7. **渐进收敛,不重写。** 见 ADR-3。

## 6. 收敛路线(P0 → P4)

**严格自底向上**——AI 基座依赖下面全部,任何一层不可信,上面的 AI 就是"在脏数据上把错误答案讲得更流畅"。

| 阶段 | 目标 | 解决的致命伤 | 状态 |
|---|---|---|---|
| **P0 止血** | `build`/`test`/`vet`/CI 全绿;标 dev-only | "测试网破、不可信" | ✅ 已确认全绿(33 包/18 个有测试全 PASS) |
| **P1 真相层收敛** | 5 套 → 三层骨架;mainline 定为业务拓扑真相,拆/冻结 v2 在拓扑的越界,legacy 退兼容 | **多套真相并存(最大劝退点)** | 📄 计划见 [`P1-...`](./P1-truth-layer-convergence.md) |
| **P2 元数据统一** | A/B 两套动态模型合一;去分区 | schema 冗余,NL/前端不知信谁 | 待 |
| **P3 关系图落地** | 第一层可信关系图(简单 PG 建模)+ 事件流 + 期望态/实际态 | 影响分析/异常检测没有基座 | 待 |
| **P4 AI 层** | NL 查询 / 自动发现 / 影响分析 / drift,经 MCP 暴露 | "下一代"的脸面 | 待 |

## 7. 决策记录(ADR)

### ADR-1:mainline 是正统设计,不是失控垃圾

[`MAINLINE_MODEL_PROPOSAL.md`](./MAINLINE_MODEL_PROPOSAL.md) 是项目**唯一**正面、详尽、对标蓝鲸的拓扑真相层设计提案。`mainline_instances` 表(提案行 184-202)、`topology.Service` 双写 mainline(提案"阶段2 兼容写")、9 个 `/mainline` 端点,全部对得上蓝图。它只是没走完。**因此终局复活 mainline、走完提案,而非另起炉灶。**

### ADR-2:v2 不扶正(理念吸收,实现不复用)

- **无设计背书**:`0af24bd`(2026-04-03)一次性 +4151 行 AI 生成,零注释、零 doc、零 commit rationale;同日把 `docs/plans/` 整个 gitignore。本地与库均无任何 v2 设计文档。
- **方向与提案相悖**:提案产品目标第 1 条 + 最终结论(行 34 / 424-435)**明确反对**把业务拓扑"退化成普通动态关系图"——正是 v2 在做的。
- **实现不可信**:8 条一致性硬伤(`edges_v2` 无唯一约束、建节点非原子、`CreateResource/Edge` 不去重无锁、字符串嗅探静默回退吞错、`nextRefID` 并发不安全……);测试 100% SQLite 假绿。
- **复杂度方向也错**:为"通用/规模"堆 partial unique/GIN/JSONB/ON CONFLICT 却没做对,而我们要的是"10 万、清晰、可开源"——为不需要的规模背复杂度还做不对 = 双输。
- **裁定**:吸收其"通用图 + 事件"**理念**到第一层(P3),用最朴素可信的 PG 建模**重做**;不复用、不扶正现实现。

### ADR-3:渐进收敛,不重写

**v2 本身就是"重写一套更好的"思维的产物**(绕开 3 月的 mainline 蓝图、一次性生成),结果是又多一套并存 + 一堆硬伤。**再来一次重写就是第三次重蹈 AI 失控。** 而现有代码并非全废:mainline 是好设计的正统实现、动态模型引擎有真实流量、测试已绿。渐进收敛每步可验证、持续可用——这正是开源产品需要的节奏。
