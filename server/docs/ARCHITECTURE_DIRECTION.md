> 本文记录 Wende CMDB 的架构目标和关键决策。与本文冲突的设计，应先更新本文再实施。
>
> - 决策日期：2026-05-30
> - 相关文档：[`MAINLINE_MODEL_PROPOSAL.md`](./MAINLINE_MODEL_PROPOSAL.md)（主线模型方案）、[`P1-truth-layer-convergence.md`](./P1-truth-layer-convergence.md)（P1 计划与实施记录）

---

## 1. 背景

2026-05-30 做出这些决策时，同一份业务拓扑和资源数据由多套实现并存表达，彼此没有明确的主次关系：

- **旧表**（`sets` / `modules` / `host_module_relations`）：当时生产环境唯一的写入来源。
- **主线模型**（`mainline_instances`）：`MAINLINE_MODEL_PROPOSAL.md` 的实现，只完成到兼容写入阶段。
- **v2 图**（`resources_v2` / `edges_v2`）：HTTP 层优先读取的投影，没有设计文档，也不在正式迁移中，只在开启 `ENABLE_COMPAT_AUTOMIGRATE` 时建表。因此纯生产部署下这些表不存在，拓扑读取会回退到旧表。
- **两套动态模型**（`models` / `model_instances` 和 `dynamic_models` / `resources`）：功能重叠。

对开源项目来说，贡献者和使用者都需要能确定哪份数据才是准的，所以收敛数据来源是其他工作的前提。

## 2. 产品定位

| 维度 | 定位 | 推论 |
|---|---|---|
| 性质 | 开源 CMDB，业务模型参考 [BK-CMDB](https://github.com/TencentBlueKing/bk-cmdb) | 架构要容易理解和讲清楚 |
| 规模 | 约 10 万资源 | 不做分区表、懒投影等过早优化，用朴素的 PostgreSQL 建模 |
| 差异点 | AI 原生能力，以及通过 MCP 提供给 agent 的工具接口 | CMDB 要成为 agent 可信赖的事实来源 |

## 3. 目标架构

三层结构来自 `MAINLINE_MODEL_PROPOSAL.md`，并在其上增加 AI 能力层：

```
┌───────────────────────────────────────────────────────────┐
│  AI 能力层          自然语言查询 · 自动发现 · 影响分析 · 漂移检测     │
│                  —————  通过 MCP 提供给外部 agent  —————        │
├───────────────────────────────────────────────────────────┤
│  第三层  业务拓扑产品语义        /api/v1/topology（稳定接口）        │
├───────────────────────────────────────────────────────────┤
│  第二层  主线模型               业务拓扑这棵树（有约束、高频、树形）     │
├───────────────────────────────────────────────────────────┤
│  第一层  通用动态模型 + 关系图    任意资源 / 任意关系 / 依赖与影响分析   │
├───────────────────────────────────────────────────────────┤
│  横向能力     强身份 + 幂等  ·  事件流  ·  期望状态与实际状态对账       │
└───────────────────────────────────────────────────────────┘
```

- **第一层**：模型元数据、实例和任意类型之间的关系图，承载主机、网络设备、中间件、数据库和自定义配置项，并支持跨类型的依赖遍历。
- **第二层**：业务拓扑（`business → set → module`）是有约束的树（固定层级、唯一父节点、默认节点、排序、路径），用树模型而不是通用图来保证约束和查询效率。
- **第三层**：对外保持 `/api/v1/topology/*` 接口稳定，由主线模型驱动，前端不需要理解元模型。
- **AI 能力层**：把第一、二层的查询和分析能力通过 MCP 提供给 agent 编排，不在 CMDB 内置聊天逻辑。
- **横向能力**：强身份和幂等支撑自动发现，事件流支撑变更查询和审计，期望状态与实际状态的对账支撑异常检测。

## 4. 设计原则

1. **单一事实来源。** 一个实体只有一份权威数据。
2. **强身份和幂等。** 每类资源有明确的身份键，重复写入（尤其是自动发现）不产生重复或孤儿数据。
3. **按需使用图。** 四类 AI 能力里只有影响分析真正需要图。自然语言查询需要强 schema，自动发现需要幂等写入，异常检测需要事件流和对账。树、图、实例各用最合适的结构。
4. **CMDB 是 agent 的工具。** 它负责提供可信的事实和工具接口，自然语言理解和编排交给外部 agent。
5. **期望状态和实际状态分离。** CMDB 存期望状态，采集器上报实际状态，两者对账产生漂移。
6. **按 10 万规模设计。** PostgreSQL 单库加普通索引即可，性能优化等真正出现规模压力时再做。
7. **渐进收敛，不重写。** 见 ADR-3。

自底向上推进：AI 能力依赖下面各层的数据质量。

| 阶段 | 目标 | 状态（2026-11-09 按代码核实） |
|---|---|---|
| P0 稳定基线 | 构建、测试、`vet` 全部通过 | 已完成 |
| P1 数据来源收敛 | 主线模型作为业务拓扑的权威数据，主机归属统一到 `host_node_memberships` | 核心已完成，见 [实施记录](./P1-truth-layer-convergence.md)。`host_module_relations` 已删除，`core/projection` 已移除 |

## 6. 决策记录

### ADR-1：以主线模型作为业务拓扑的基础

**决策：** 走完 `MAINLINE_MODEL_PROPOSAL.md` 的方案，不另起一套。

**理由：** 这份提案是项目中唯一详尽的拓扑设计。`mainline_instances` 表、`topology.Service` 的兼容写入和 `/mainline` 接口都与提案一致，只是尚未完成。

### ADR-2：不采用 v2 图的现有实现

**决策：** 把"通用图 + 事件"的思路吸收到第一层（P3），用简单的 PostgreSQL 建模重新实现，不复用现有 v2 代码。

**理由：**

- **缺少设计依据：** v2 由一次大提交（`0318b93`，2026-04-03，+4151 行）引入，没有设计文档和说明。
- **与提案方向相反：** 提案明确反对把业务拓扑退化成普通的动态关系图。
- **存在一致性问题：** 例如 `edges_v2` 没有唯一约束、建节点不是原子操作、`CreateResource` / `CreateEdge` 不去重也不加锁、字符串判断失败时静默回退、`nextRefID` 并发不安全。
- **测试覆盖不足：** 测试只跑 SQLite，覆盖不到 PostgreSQL 的行为。
- **复杂度与目标规模不匹配：** 它引入的部分唯一索引、GIN、JSONB 等复杂度，10 万资源的规模并不需要。

### ADR-3：渐进收敛，不重写

**决策：** 在现有代码上分阶段收敛，不整体重写。

**理由：** v2 的经历说明，绕开已有设计另写一套，结果只是多一套并存的实现。现有代码里主线模型符合设计，动态模型引擎已在使用，测试也已通过。渐进收敛让每一步都可验证，系统也能持续可用。
